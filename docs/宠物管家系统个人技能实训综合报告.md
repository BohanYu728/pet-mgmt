# 项目一 宠物管家系统
## 1 项目介绍
### 1.1 摘要
宠物日常照护涉及档案维护、健康记录、提醒、体重变化和生活日志，相关信息分散时，用户难以形成连续的照护记录。宠物用品购买、医院查询和咨询信息又分属不同场景。为此，本项目在保留原有宠物管家业务的基础上，设计并实现一套面向宠物主人、商户和管理员的 Web 系统，将照护、服务查询、商品交易及智能辅助入口组织到统一的数据和权限框架中。
系统采用 Spring Boot、Vue 3 和关系数据库，使用 REST 接口连接独立前后端。用户 CRUD 通过 MyBatis 实现，其他业务保留 JPA；认证使用 BCrypt、Cookie JWT 与 CSRF 校验，并在角色授权之外检查对象归属。资料问答模块将项目资料切块，通过兼容模型接口完成向量检索与对话生成；模型未配置或结果不能核验时，明确返回资料原文。演示模式在 H2 内存数据库中初始化虚构样例，支持三种角色快捷体验以及六项智能功能的可编辑样例。
本报告按课程模板整合五项个人技能实训，围绕需求、架构、领域模型、数据库、代码实现和测试结果展开。已有本地验证记录覆盖业务接口、角色界面和 AI 样例提交流程。结果支持已覆盖流程能够运行，但不能据此推断模型准确率、生产环境性能或真实支付成功。研究与实现的价值在于建立可追溯的工程流程，使 AI 辅助开发的产出经过代码审查、自动测试和界面验证后再进入项目。
关键词：宠物管理；前后端分离；角色权限；AI 辅助开发；检索增强生成
### 1.2 Abstract
This project implements a web-based pet management system for pet owners, merchants, and administrators. It integrates pet profiles, care records, reminders, hospital information, shopping, and intelligent assistance while preserving the existing business scope. A Spring Boot backend and a Vue 3 frontend communicate through REST APIs. MyBatis supports user management, while JPA maintains other domain entities. Authentication combines password hashing, cookie-based JWTs, CSRF protection, role permissions, and ownership checks.
A document assistant retrieves project materials and can call a compatible model service for embeddings and response generation. When the service is unavailable or citations fail validation, the assistant returns clearly identified source excerpts. An isolated demonstration environment provides editable business data and six intelligent feature samples. This report follows the course template and combines five practical exercises with requirements analysis, UML design, implementation details, and traceable testing evidence. Local results demonstrate the covered workflows; they do not establish model accuracy, production readiness, or real payment processing.
Keywords: pet management; REST API; role-based access control; AI-assisted development; retrieval-augmented generation
### 1.3 项目背景与问题定义
本项目关注信息组织和业务协同，而非替代专业诊疗。宠物主人需要把同一只宠物的疫苗、驱虫、体重和异常观察联系起来；商户需要管理自己的商品与订单；管理员需要处理平台治理。若所有入口同时展示给所有角色，界面会变得拥挤，也容易使使用者误解自己的职责范围。因此，需求不仅是增加功能，还包括清晰区分角色工作台、限定数据访问范围，并提供可以实际操作的样例。
旧工程已经具有宠物、健康、商城和智能分析等业务内容。本次工作将个人技能实训要求落实到工程结构、接口交互、协作配置、安全和模型应用，避免为了更换框架而重写全部领域关系。报告研究对象是当前可运行项目及其证据记录，结论以本地工程验证为边界，不作商业产品成熟度或算法有效性的外推。

### 1.5 功能需求与角色边界
| 角色 | 主要需求 | 界面与数据边界 |
| --- | --- | --- |
| 宠物主人 | 管理宠物及照护记录、医院查询、商城订单、六项智能功能 | 只展示主人工作台；写入及私有记录读取检查归属 |

需求划分遵循“导航可理解、接口可校验”的原则。隐藏菜单只是改善体验，不能代替服务器授权。手动访问其他角色页面时，前端将用户引导回本角色首页；直接调用受保护接口时，后端根据认证身份、权限和资源归属作出判定。
### 1.6 非功能需求与范围
可维护性要求业务规则集中在 Service，Controller 负责输入和响应，前端使用统一接口客户端。安全性要求密码不明文入库、签名密钥不进入源码、认证令牌不放入浏览器可直接读取的持久存储。可用性要求图片失败有回退、空列表与错误有说明、手机菜单可收起、AI 服务失败有明确状态。
本次没有制定并验证并发吞吐量、可用率或模型准确率的数值指标，不能把单次浏览器成功作为这些指标达标的证据。真实支付网关、在线租金缴费、生产 MySQL 迁移、真实模型服务及云端 CI 均不属于已证实完成的运行结果。

### 1.7 典型业务场景与需求推导
#### 1.7.1 连续照护场景
以虚构宠物旺财为例，主人首先建立宠物档案，填写名称、物种、出生日期和档案体重，再按实际照护时间添加健康记录、体重历史和日常日志。档案描述相对稳定的信息，历史记录描述某一时间点发生的事情，两者不能互相覆盖。若只反复修改档案中的体重，就会丢失变化过程；因此系统同时保留档案值与体重记录，并通过趋势页面帮助用户回看。
提醒承担把照护计划转化为后续行动的职责。用户查看提醒后可以维护已读或忽略状态，但状态变化不意味着健康事项已经完成。报告将健康记录和提醒分别建模，使观察事实、计划安排和阅读状态具有各自的数据语义。异常饮食或活动情况可以写入日志，随后作为咨询描述的参考；模型输出仍需与原始观察核对。
这一场景推导出三个具体需求：私有记录必须围绕所属宠物组织；记录日期和内容要能够解释；查询与修改不能只依据页面传来的用户编号决定权限。页面方便用户操作，后端依据当前认证身份确定可访问的数据范围。管理员治理功能另有授权入口，不能以普通用户的照护页面承担平台管理职责。
#### 1.7.2 消费与商户经营场景
主人浏览商品、查看详情、选择数量并加入购物车，再填写收货信息完成订单创建。商品列表显示当前价格和库存，订单明细保存成交时的快照。价格后来调整时，旧订单仍应能够解释当时购买的商品和金额，因此商品对象与订单明细不能只用实时关联替代历史信息。
商户从本店商品维护进入订单处理，用户从自己的订单列表查看结果。双方操作同一条交易链路，但职责不同：买家发起购买，商户处理本店商品及相关订单，管理员处理账号和入驻治理。租金账单页展示虚构账单与查询结果，当前项目没有把它扩展为在线缴费。划分工作台有助于把任务放在角色需要的位置，也使权限验收更容易定位。
#### 1.7.3 平台治理与演示场景
商户注册后存在审核状态，管理员在商户审核入口处理入驻信息；普通用户注册则走自身账号流程。平台统计和用户管理为管理员提供治理视图。审核状态、角色身份和资源归属是不同维度：具有商户身份不代表任何状态下都能登录经营，成功登录也不代表可以修改其他商户的商品。
教学展示需要快速进入可操作状态，所以 demo 环境提供三类账号和虚构数据。样例是降低体验门槛的辅助入口，业务操作仍经过正常服务。与只展示静态界面相比，这种方式能够观察提交、保存和刷新后的结果；与真实运营数据相比，它又便于重复演练和恢复初始化状态。
### 1.8 实现方法与成果组织
项目采用从现有工程到可验证闭环的实现方法。首先盘点业务与数据结构，保留已有照护和交易模型；随后补充分层用户管理、统一接口客户端和角色导航；再审查认证、授权和事务边界；最后把智能入口和演示数据接入正常业务链路。每个阶段的结果分别由源码、测试记录和界面截图支撑。
本报告的内容组织对应这一过程：需求说明为什么需要功能，设计说明模块如何协作，代码说明关键规则由何处执行，运行结果说明哪些路径已有证据，反思说明不足和改进依据。五项实训是同一项目的工程能力组成，而不是五套互不关联的系统。报告中的样例名称、订单和账单为演示数据，不能作为真实用户访谈、临床样本或商业成交的依据。

## 2 相关开发技术
### 2.1 Spring Boot、Maven 与分层持久化
后端使用 Spring Boot 3.4.5，编译目标为 Java 17。Spring MVC 将请求映射到 Controller，并以 JSON 连接前端；内嵌容器允许直接运行打包后的 jar。官方文档描述了 REST Controller 与 HTTP 映射机制[1]，本项目据此组织业务接口，具体版本以 pom.xml 为准。
Maven 负责依赖、编译、测试和打包。用户管理需要满足 MyBatis 实训要求，因此使用 Mapper 参数绑定 SQL；其余领域对象继续采用 JPA Repository。两种持久化方式的边界是功能模块，不应在同一业务写入中随意混用缓存状态。用户和角色关系更新在同一事务中完成，关联数据存在时拒绝删除用户。
### 2.2 Vue、Axios 与 RESTful 接口
Vue 3 用于组件化页面与响应式状态管理，Vue Router 组织独立工作台，Vite 提供开发代理与静态构建。Vue 的官方说明将声明式渲染和响应式作为核心能力[2]。本项目在此基础上将列表、表单、弹窗与状态提示组织为可复用交互，不在页面中直接访问数据库。
Axios 客户端设置统一 API 前缀、凭据和超时；写请求携带 CSRF 头。开发时由 Vite 转发 /api 和 /uploads，部署时可以采用同源反向代理或明确的跨域配置。携带 Cookie 的跨域请求必须配合精确来源白名单，不能同时采用任意来源通配符。
REST 接口以资源为中心组织列表、详情和修改操作，但项目中仍保留部分历史路径和业务动作接口。报告不将其描述为完全符合全部 REST 约束。OpenAPI 用于查看请求与返回结构，字段含义、错误分支和权限仍需结合 DTO 与实际测试核对。
### 2.3 Spring Security、JWT 与 RBAC
认证回答“当前是谁”，授权回答“可以执行什么”，归属校验进一步回答“是否能操作这条记录”。三者承担不同职责。密码经 BCrypt 哈希保存；服务端签发 JWT，并通过 HttpOnly Cookie 发送。前端读取的 CSRF token 与认证 JWT 不同。退出除清除 Cookie 外，还维护令牌撤销信息。
由于浏览器会自动附带 Cookie，使用无状态 JWT 并不意味着可以忽略 CSRF。Spring Security 官方资料说明了 CSRF 防护机制及 token 处理[3]。项目为写请求启用独立 CSRF 校验，并限制跨域来源。正式部署仍需 HTTPS、安全 Cookie 和适当的密钥管理。
### 2.4 Git、代码评审与持续集成
Git 分支用来隔离工作，合并时处理冲突，提交记录提供变更追溯。项目保留 feature 分支工作方式、PR 模板和 GitHub Actions 配置。工作流表达构建与测试要求，PR 模板提示修改范围、验证方法和风险。
本地已经执行冲突练习并保存记录；远程 PR、人工 Code Review 和云端 CI 未实际执行。AI 可提供 PR 摘要和潜在问题，但摘要不能证明实现正确，工作流文件存在也不能证明远程任务通过。最终责任需要由开发者和评审者依据代码与结果承担。
### 2.5 提示工程、兼容 SDK 与 RAG
提示工程将任务、允许资料、输出格式和失败行为明确表达。资料助手将固定政策放在 System 消息，资料和问题放在 User 消息，并提示模型把其中的指令当作不可信数据。SDK 封装 embeddings 和 chat/completions；后端环境变量控制服务地址与模型名称，浏览器不持有 API Key。
RAG 将检索内容作为生成依据，相关论文讨论了检索与生成结合的知识任务方法[4]。本项目只实现小规模工程原型：按 Markdown 小节切块、请求向量、余弦排序、选择前三段、生成答案并校验引用。它没有实现论文中的全部训练与评估方法，也没有以业务截图证明论文级效果。
无可用模型时，助手改用词法检索并返回资料原文；有模型时，索引向量在进程内缓存。仅支持聊天而不支持 embeddings 的服务不能完成这里的完整向量检索链路。引用校验能限制虚构来源 ID，却不能证明每句回答与来源语义一致。

### 2.7 技术选型依据与工程取舍
Spring Boot 将 HTTP 服务、依赖注入和安全配置组织在统一运行环境中，适合本项目的模块化单体。选择它的依据是现有 Java 工程基础及课程要求，不是对所有框架作性能优劣排名。Maven 的依赖和构建声明使开发、测试与部署使用同一工程入口，减少手工复制 jar 带来的版本不一致。
用户 CRUD 使用 MyBatis 可以明确呈现 SQL、参数和映射的关系，便于实训讲解；保留其他业务的 JPA 则避免重写已有实体关系。代价是维护者需要同时理解两种持久化方式，明确事务范围与对象生命周期。因此报告按模块解释其职责，后续演进应结合维护成本决定是否统一，而不是继续无边界地增加数据访问方式。
Vue 的组件化适合表单、列表、导航和弹窗等重复交互，前后端分离使字段约定成为双方协作的中心。系统没有另建复杂的分布式服务，因为当前教学规模更需要清晰的业务闭环与可复现部署。H2 则服务于隔离演示和测试，不能据此推断 MySQL 方言、索引及事务行为完全一致。
模型调用通过 AiGateway 抽象隔离，业务服务不直接拼接网络协议。这样能够在测试中替换网关，检查异常和引用处理；也便于将来调整兼容服务。抽象隔离的是调用边界，模型版本、数据质量和回答正确性仍需独立验证。若项目规模扩大，再依据资料数量、更新频率和查询延迟决定是否引入持久向量索引。

### 3.2 系统架构与模块职责
组件关系如图3-2。Vue 页面只通过接口访问业务，Security 在业务入口之前建立身份上下文；Controller 验证请求结构，Service 执行事务与归属判断，Mapper 或 Repository 负责持久化。AI Gateway 将外部模型依赖隔离，文件操作集中在上传工具中。

### 3.3 登录与权限详细设计
登录时序见图3-3。提交前获得 CSRF token，后端查找用户并核验哈希；成功后签发 JWT，将认证 Cookie 交给浏览器管理。后续请求经过 JWT 验签、撤销检查、权限判断及业务归属校验。失败时应返回可处理的错误，前端不把失败结果当作已登录状态。
![图3-3 登录及后续请求时序图](diagrams/login-sequence.png)
RBAC 使用 users、roles、permissions、user_roles 和 role_permissions 表。用户角色关系与旧 users.role 兼容，由角色分配服务维护；接口通过 authority 和方法级注解限制管理操作。迁移脚本补充关联表，不应在生产库直接运行清空式演示初始化。
安全规则还包括密码字段不进入普通响应、上传路径受控、非法数量和价格拒绝、对象 ID 不作为授权凭据。AI 输入侧限制问题长度和控制字符，并把资料内指令视为不可信内容。这些措施降低已识别风险，但不是对所有提示注入或所有应用漏洞的完整证明。

### 3.5 智能功能与 RAG 详细设计
六项入口是资料问答、品种识别、情绪分析、健康报告、商品推荐和症状咨询。界面为每项提供可编辑输入样例，并在提交后通过正常业务接口产生结果。填入样例不会自动请求模型；照片可替换为自己的文件，加载失败有重试入口。历史记录由实际提交生成，而非预置一张固定答案图。
RAG 活动流程如图3-6。KnowledgeCatalog 按二级标题切块，每块最多约450字符，保留资料 ID；AssistantService 在模型可用时缓存资料向量，对问题向量计算余弦相似度，筛选大于0.15的结果并取前三项。参数是当前原型的实现选择，未经系统性调参实验，不能称为最优值。
![图3-6 资料问答的检索、生成与降级活动图](diagrams/rag-activity.png)
生成提示包括固定 System 政策、带 ID 的资料与用户问题。返回内容必须有合法引用，引用 ID 只能来自本次检索集合；异常、无合法引用或模型不可用时返回原文，并明确 status。没有匹配资料时返回 no_sources。引用格式检查与语义正确性之间仍存在距离，应由使用者查看原文核对。
其他智能入口保留原系统算法。品种模块当前是颜色启发式猫分类，固定75%的显示值不是实测准确率；情绪模块根据图像颜色、边缘等特征给出参考；健康模块使用500条合成记录训练的本地模型，不能替代真实医学评估。推荐和咨询在无外部服务时使用本地算法或规则，报告分别说明这些限制。
#### 3.5.1 向量检索与词法降级原理
向量检索把问题和资料映射到同一向量空间。设问题向量为 q，资料向量为 d，余弦相似度等于两者点积除以各自长度的乘积，即 cos(q,d)=(Σqᵢdᵢ)/(√Σqᵢ²·√Σdᵢ²)。当前实现检查维度和数值有效性，零长度向量的相似度按0处理，避免无效数值进入排序。相似度用于排序相关候选，不等同于回答正确的概率。
资料向量首次建立后在进程中缓存，可以减少后续请求重复向量化相同资料的开销；问题向量仍按请求生成。该缓存适合当前小规模、随应用加载的项目文档。如果改为用户在线上传并更新知识库，则需要新增版本标识、失效重建和持久化策略，不能让旧向量继续对应已经变更的正文。
词法降级将问题去除标点和空白，以相邻两个字符组成的片段匹配资料标题及正文，再按命中数排序。它能在没有模型凭据时提供资料入口，但对同义表达、短问题和语义歧义的处理有限。向量和词法检索都取最多三段，目的在于限制原型上下文规模；参数是否合适还需固定问答集及人工相关性标注来评价。
#### 3.5.2 提示结构与结果可解释性
System 提示限定资料范围、引用方式和健康建议边界；User 消息分别装入带资料 ID 的内容和问题。将固定政策与外来内容分开，有助于说明信任边界。资料中的“忽略规则”或“输出密钥”等文字不应被提升为系统要求。当前网关设置20秒超时、关闭 SDK 自动重试，并限制生成 token 数，避免交互无限等待和异常时反复调用。
结果包含 answer、sources 和 status，前端应同时展示答案、来源与模式。answered 表示生成结果通过当前引用格式校验；retrieval_only 表示展示资料原文；no_sources 表示没有相关资料。这三种状态让使用者能够区分生成、检索和资料不足，而不是把所有响应统一包装成可信智能答案。
引用检查还限制空回答、过长回答和检索集合之外的 ID。若一个回答同时带有合法和伪造 ID，当前服务会放弃该生成结果并降级。即使 ID 全部合法，也可能存在断章取义或事实推断错误，因此来源检查只是验证的一部分。更完整的质量评价应检查证据是否支持具体句子，以及资料本身是否准确、完整和及时。

### 3.8 数据组织与接口契约补充设计
#### 3.8.1 数据冗余与历史可追溯性
数据库中的冗余需要区分有意的业务快照与需要同步的重复字段。订单明细保存商品名称和价格属于有意快照，反映成交事实；users.role 与角色关系表并存则属于兼容旧工程的状态，需要由角色分配服务统一维护。前者不应随商品更新而改写，后者若分别修改就可能造成授权不一致。
照护记录中的日期与数据库写入时间也具有不同含义。用户可能今天补录昨天的观察，因此历史查询应解释业务发生时间，而不能一律以入库顺序替代。档案体重和体重历史的关系应保持明确：一个是当前档案属性，一个是趋势依据，页面和报告均不把两者描述为自动同步的唯一数值。
查询通常围绕主人、宠物、商户和订单展开。正式数据库可结合这些过滤条件以及时间排序检查索引需求，但是否建立复合索引应依据实际 SQL、数据分布和执行计划。当前报告没有性能压测或生产执行计划，不将索引建议写成已经实现的性能优化结果。
#### 3.8.2 请求与响应的责任划分
Controller 或 DTO 首先检查必填项、类型和基本范围；Service 再判断账号状态、对象归属、库存与状态迁移。前端校验用于尽早提示，后端校验决定请求能否执行。请求中的 userId、merchantId 或资源编号必须结合服务器认证身份解释，不能因为字段看起来正确就跳过权限判断。
接口契约既包括正常 JSON 字段，也包括拒绝和失败。前端统一错误函数优先显示服务端的 error 字段，并为400、401、403、404、409及服务异常提供默认说明。某些历史业务采用响应体中的错误标记，客户端还需通过 unwrap 检查业务结果；因此不能只依据 HTTP 200 判定业务已经成功保存。
API 文档可以辅助发现字段差异，但接口联调还需要比较表单输入、请求 JSON、后端 DTO、数据库字段和返回结果。例如收货地址使用多个字段保存快照，宠物照片涉及上传路径，分页列表返回数据与总页数。字段映射应逐项核对，避免 AI 自动生成组件时把其他页面的命名规则直接套用。
#### 3.8.3 文件、隐私与运行环境边界
照片和商品图片由上传能力管理，数据库保存路径等关联信息。文件存储与数据库事务不是同一种资源：数据库回滚不必然恢复已经删除的文件，删除记录也不意味着外部备份立即消失。因此正式运行应增加孤立文件检查、上传限制和备份恢复流程；这属于后续完善事项，当前截图只能证明对应上传与展示路径。
账号资料、收货联系信息及照护观察属于需要限定访问的数据。演示环境使用虚构内容，正式环境应减少不必要字段收集，并制定备份访问和数据保留规则。JWT Cookie、CSRF token、密码哈希和模型 API Key 分属不同用途，日志与截图不得把它们作为调试内容公开。密钥通过环境变量配置，也需要结合实际部署限制环境与日志的读取权限。

### 4.4 实验四：JWT、CSRF 与方法级权限
注册密码采用 BCrypt；签名密钥与数据库凭据由环境变量读取。SecurityFilterChain 保留 CSRF，并将 JWT Filter 放在认证过滤器链中。以下为 SecurityConfig 的真实配置节选。
<!-- code:csrf:start -->
```java
        CookieCsrfTokenRepository csrfRepository = CookieCsrfTokenRepository.withHttpOnlyFalse();
        csrfRepository.setCookiePath("/");
        http.csrf(csrf -> csrf.csrfTokenRepository(csrfRepository)
                .csrfTokenRequestHandler(new CsrfTokenRequestAttributeHandler()))
```
<!-- code:csrf:end -->
CookieCsrfTokenRepository.withHttpOnlyFalse 使独立 CSRF Cookie 可被前端读取，以便写入请求头；它不是把认证 JWT 暴露给脚本。JWT Cookie 仍由登录控制器设置为 HttpOnly。方法级授权与 Service 归属校验共同限制管理、宠物和订单接口。
密码应保存不可逆哈希，密钥则应保存在服务端受控配置或密钥管理环境，不能把“所有敏感数据入库加密”理解为保存可逆用户密码。提示输入防护采用长度、字符、固定政策和引用校验，验证重点是非法输入、越权和失败路径。

### 4.7 从请求提交到结果确认的实现闭环
#### 4.7.1 Axios 请求与 CSRF 协同
统一客户端对非 GET、HEAD、OPTIONS 请求先调用 ensureCsrf，再按返回的头名附带 token。csrfRequest 用于合并同一时间的初始化请求，完成后清理引用，避免多个表单同时提交时重复拉取。收到403时会使缓存状态失效，但拦截器没有自动重放写请求，避免用户不知情地重复创建记录或订单。
withCredentials 让浏览器按规则携带认证 Cookie，页面无需读取 JWT。用户信息通过会话查询维护，权限入口依据服务端返回的角色组织。当前身份变化时，前端路由与界面需要重新确认，而不是继续相信旧的本地菜单状态。网络超时和服务拒绝应作为失败呈现，不能在请求未完成时先显示保存成功。
#### 4.7.2 库存条件更新的必要性
在进入结算时读取到有库存，不代表稍后写入时库存仍然足够。两个购买者可能同时通过预校验，因此扣减操作还需把“库存足够”写入更新条件，并检查受影响行数。条件失败后抛出异常，使同一订单内已经完成的数据库写入回滚，防止一部分商品成功扣减而订单整体失败。
同一用户购物车加锁与商品库存条件更新解决不同问题：前者有助于控制同一购物车的并发修改，后者防止不同用户竞争同一商品时依据旧库存写入。订单取消还必须验证当前状态，避免重复请求多次回补库存。现有测试覆盖选定异常路径，但并未量化高并发吞吐量，因此这里解释的是规则与验证对象，而不是性能结论。
#### 4.7.3 智能功能样例与真实提交
AI 样例按钮只设置表单值或加载图片，用户仍可修改后提交。普通用户提交会调用与手动填写相同的接口，产生正常结果或分析历史。由此可以同时验证填入、替换、提交和展示；若样例按钮直接输出固定文本，则无法检验接口、认证和保存链路。
资料助手的 ask 函数先验证输入，再选择向量或词法路径，并集中处理失败状态。测试网关可以构造空向量、异常或非法引用来检查后端控制逻辑；浏览器截图则证明页面能够显示相应模式。二者互补，但都不能替代真实外部模型的回答质量评估。

### 5.11 运行结果的阅读方法与问题定位
#### 5.11.1 截图、接口和持久化的对应关系
功能截图展示某一时刻的可见状态，接口记录展示请求的处理结果，持久化检查或刷新后查询展示数据是否被保存。判断一个功能闭环，应把这三类证据联系起来。注册页面出现并不证明账号创建成功，购物车显示商品并不证明库存已扣减，AI 页面出现报告也不证明报告内容正确。
本报告因此在截图旁保留入口和操作说明，并在测试用例中列出输入、预期和已记录结果。账号、照护、商品、订单与分析历史等功能分别对应可复现入口。商户审核截图展示当前列表，完整审核过程还需接口记录支撑；商品和账单中的金额为虚构样例，不能据此推断真实收付款能力。
#### 5.11.2 分层定位失败原因
页面操作失败时，首先确认当前角色、运行 profile 和请求路径，再检查浏览器返回状态及业务错误内容。401优先排查会话是否有效；403需区分角色授权、对象归属与 CSRF；409或库存错误应回到业务状态和库存条件，而不是反复修改前端表单。没有响应还可能涉及代理、超时或服务启动问题。
若接口返回成功但页面没有更新，应继续检查返回字段、前端状态和重新查询结果；若数据库没有变化，应核对事务是否回滚、请求是否进入正确环境。图片异常需要分别检查文件 URL、上传结果与回退行为；地图异常要区分医院数据和瓦片网络。分层定位能避免把所有失败笼统归因于“功能坏了”。
#### 5.11.3 AI 输出评价与后续实验方案
AI 原型的评价分为工程可用性和内容质量。当前证据主要覆盖工程侧：请求能否提交、模式能否说明、异常是否降级、结果是否可见。内容侧需要固定题目、期望资料和人工判定，例如问题对应的资料是否进入前三项、回答中的关键事实是否得到引用支持、资料不足时是否拒绝猜测。
后续可建立包括正常问题、同义改写、无资料问题和注入指令的测试集，分别记录检索命中、引用有效性、语义正确性与请求延迟。调整切块长度、相似度阈值或模型后，使用同一测试集比较，并保存服务与模型版本。评价结果必须使用实际测量值，不能用界面中的固定置信度或 HTTP 成功率代替算法准确率。
品种与情绪入口还需要有明确标签和来源的图片数据，并检查未支持物种、遮挡、低清晰度和背景变化等情况。健康与咨询需要专业复核及更严格的数据适用范围。当前报告未开展这些实验，因而将其列为改进方案，以避免把可演示原型写成已经验证的专业智能系统。

## 6 心得（使用AI情况）
### 6.1 总结与反思
项目将五项技能实训落实为同一宠物业务系统中的工程能力。分层 CRUD 使请求到数据库的路径可解释，前后端分离使接口契约成为联调中心，Git 与 CI 配置使变更可追溯，认证与授权限制操作范围，RAG 原型则把资料和智能回答联系起来。三种角色工作台与可操作样例让系统更容易展示，也使报告中的功能证据能够对应真实入口。
主要经验是先明确业务边界，再采用工具辅助。仅增加页面或生成代码不能解决角色职责和数据归属问题；仅展示模型输出也不能证明算法有效。工程验证需要同时核对页面、接口、存储和异常路径，智能验证还需关注资料、引用与语义。
此次文档按模板六部分组织，避免将五份报告机械拼接。UML 用于解释职责、关联和流程，代码节选用于解释关键控制点，截图用于说明运行状态。三类证据互相补充，但不能互相代替。能讲清楚它们之间的对应关系，才表明开发者理解项目。
### 6.2 五项实训的具体反思
实验一的难点在于新增 MyBatis 用户管理同时保持原有 JPA 领域关系。值得保留的做法是限定持久化边界，使用事务保证用户与角色一起更新，并在关联存在时拒绝删除。待完善的是在真实 MySQL 上验证迁移、约束和方言差异。
实验二的难点在于字段映射、Cookie、CSRF 和跨域共同作用，而非单纯写出 Axios 请求。统一客户端和错误提示降低重复处理，角色工作台减少无关入口；仍应补充正式部署的反向代理、缓存和外部地图异常验证。
实验三建立了本地冲突练习、PR 模板与 CI 定义，但缺少真实远程协作证据。AI 可以概括变更和指出疑点，不能代替人工解释冲突两侧的业务含义，也不能替代云端日志。
实验四需要区分密码哈希、认证令牌、CSRF token 和 API Key。它们具有不同的用途与保存方式，不能使用同一种“加密”说法概括。角色校验之后仍需对象归属，模型输入限制之外仍需语义核验。
实验五明确了输入样例与结果之间的区别。样例只帮助形成请求，实际结果仍通过业务接口产生；降级模式使未配置模型时也能说明资料来源。下一步重点是建立质量测试集，并记录检索不足、错误引用和回答偏差，而不是继续增加看似智能的固定输出。

### 6.4 代码理解与后续改进
提交前应能够说明一次新增用户如何经过 DTO、Mapper 和事务，为什么条件库存失败需要回滚，为什么 JWT Cookie 仍需要 CSRF，以及资料问答何时返回 answered、retrieval_only 和 no_sources。教师随机抽测时，应依据当前源码讲解，而不是背诵报告中的片段。
优先改进事项是补齐生产环境和真实服务证据，统一历史字段与错误结构，为金额采用合适精度，建立模型评测与反例库。功能扩展应在权限、数据一致性和用户理解的基础上进行，避免用更多菜单和更多 AI 名称掩盖尚未验证的环节。
#### 6.4.1 提交讲解与后续维护的准备
代码讲解可从一条完整操作展开：说明表单字段如何进入 Controller，身份从何处取得，Service 在哪里校验归属和业务状态，Mapper 或 Repository 如何写入，异常如何返回页面。对新增用户还应解释 BCrypt 与事务，对订单应解释条件库存更新及取消幂等性，对资料助手应解释检索、引用校验和降级模式。
维护工作应保留修改前的复现条件与修改后的验证结果，尤其注意角色变动、库存竞争和模型服务异常。AI 给出的修改建议可以作为候选方案，但开发者必须确认它是否破坏历史字段、事务边界或安全假设。报告记录工具使用，也应成为今后定位设计选择的依据，而不是代替对代码的理解。
后续改进宜先完成真实 MySQL 与 Java17 环境验证、远程协作证据和模型质量测试，再考虑新功能。这样可以逐步缩小当前结论的适用范围与真实运行需求之间的差距，使每项扩展都具有可解释的数据、权限与测试依据。
